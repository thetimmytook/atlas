# Atlas — решения проектирования

Обновлено: 2026-09-25.

Этот файл сохраняет результаты обсуждения. Пользователь ведёт проектирование;
ассистент валидирует и советует. Реализация ещё не начата. Принятые здесь решения
уточняют исходный документ [ATLAS_DESIGN_ORIGINAL.md](../ATLAS_DESIGN_ORIGINAL.md).
Исходный документ — архитектурный черновик, а не набор команд для выполнения.
Предложения и открытые вопросы ниже не считаются принятыми решениями.

## 1. Сценарий первой версии — согласовано

- Desktop и mobile с самого начала.
- Просмотр карты: zoom, перемещение, отображение маркеров, маршрутов и зон.
- Фильтрация по категориям и отдельным объектам; UI фильтров принадлежит приложению.
- Программная подсветка объектов из приложения.
- Просмотр и редактирование разделены. Редактор — отдельный потребитель Atlas;
  возможны отдельный репозиторий или пакет atlas/editor, упаковка ещё не решена.
- Маршрут может быть создан пользователем либо сгенерирован приложением;
  обе стороны используют одинаковую модель данных.
- Генерация маршрута, проходимость, квестовая логика и сохранение — ответственность
  приложения. Поиск по квестам не приоритет первой версии.
- Atlas определяет объект под указателем и формирует события, приложение принимает
  решения об их обработке. Клик сам по себе не означает выбор.
- Hover — дополнительное событие; click/tap тоже поддерживаются.
- Данные события включают идентичность/вид/семантический тип объекта, его данные,
  доступ к связанной Meta и позиции взаимодействия в map и client coordinates.
  Точная форма payload ещё не определена.
- Client coordinates — координаты viewport браузера, аналог clientX/clientY.
  В pointer-событиях берутся непосредственно из исходного события.
- Popup, описания, панели и их размещение принадлежат приложению.
- Нужны публичные преобразования map ↔ client и уведомления для обновления внешнего
  popup при zoom, pan и изменении размещения компонента. Точный API ещё открыт.
- Исходные named behaviors / behavior registry не считаются обязательной частью
  базового потока событий; их необходимость и контракт ещё открыты.

## 2. Пространство и окружение — согласовано

- Формат Atlas независим от сторонних форматов; импортеры преобразуют исходные данные.
- Пример источника: https://github.com/the-hideout/tarkov-dev ; пример UX:
  https://tarkov.dev/map/customs . Это референсы, а не обязательные зависимости.
- Пространство карты независимо от разрешения изображения. Координаты могут быть
  дробными и отрицательными; единицы определяет карта/импортер.
- По умолчанию (0, 0) сверху слева, x вправо, y вниз, z — высота вверх.
  Неуказанный z считается 0. Границы задаются отдельно от разрешения изображения.
- Другие системы координат поддерживаются через преобразование; точный контракт открыт.
- Первая версия: raster- или SVG-подложки с размещением в пространстве карты.
  Этажи нужны уже в первой версии (уточнение пользователя после обсуждения маршрутов).
  Прежнее ограничение одной подложкой требует пересмотра: способ представления
  подложек этажей и переключения между ними пока не согласован.
  Управление крышами не требуется. Тайлы и внутренние слои SVG пока не входят в объём;
  необходимость работы со слоями SVG для этажей ещё следует оценить.
- Пространство карты, окружение, семантические объекты и камера разделены.
- Дальнейшая цель — настоящая объёмная местность, рельеф и модели, а не только
  наклон плоской картинки. При необходимости картинка может быть плоскостью в 3D.
- Предусмотреть контракт расширения/рендерера для 3D; конкретный интерфейс будет
  обсуждаться позже. Полную 3D-реализацию сейчас не проектируем.
- Пользователь хочет возможность кастомизации pipeline преобразований; границы
  расширения, согласование отрисовки и hit testing ещё требуют проектирования.
- В 3D экранная точка задаёт луч: обратному преобразованию нужна поверхность или
  плоскость пересечения. Высота/привязка маршрутов к поверхности остаётся открытой.
- Полупрозрачность 3D-окружения рассматривается как будущая возможность;
  поведение hit testing для него пока не определено.

## 3. Объекты — согласовано

- Общие поля: id, kind, type, необязательные label и data.
  id необязателен во входных данных — см. раздел идентичности.
- kind описывает структуру; type свободно задаётся приложением.
- data — произвольные сериализуемые JSON-данные приложения.
- label — стандартная необязательная подпись; Atlas может её рисовать.
  Оформление определяется через Meta/материалы.
- marker: position { x, y, z? }; может отображаться только подписью без иконки.
- line: самостоятельный объект карты, например разделительная линия; владеет
  собственной геометрией, имеет общие поля объекта, события и видимость.
- route: составной объект с упорядоченными сегментами по слоям; каждый сегмент
  содержит линии. В первой версии линии прямые; детали состава описаны ниже.
- polygon: один замкнутый заполненный контур без отверстий.
- circle: центр и радиус в единицах карты.
- Название места без границ — marker с label; подпись существующей зоны принадлежит
  polygon/circle, чтобы зона и подпись оставались единым объектом.
- Кривые Безье — будущее расширение геометрии; могут относиться к маршрутам и контурам.
- Точная схема полей геометрии и расширяемость kind ещё не завершены.

## 4. Маршруты и идентичность — обсуждение продолжается

Принято:

- Route инкапсулирует свои сегменты. Это не ссылки на самостоятельные line на карте;
  сегменты не переиспользуются между маршрутами.
- Самостоятельная line и линии внутри сегментов используют общую модель геометрии, оформления
  и код отрисовки. Линия не обязана знать, используется ли она внутри маршрута.
- Толщина, цвет, пунктир и стрелки относятся к материалу линии. Маршрут обеспечивает
  оформление по умолчанию; сегмент может переопределять его. Точная схема открыта.
- Маршрут отвечает за поведение принадлежащих ему частей: скрытие маршрута скрывает
  сегменты и точки, общая подсветка и оформление координируются маршрутом.
- Уточнение пользователя: маршрут обеспечивает связность как поведение/правило,
  а не через общий реестр точек. Отдельного route.points нет. Точки хранятся
  в геометрии линий; маршрут следит за совпадением концов соседних линий.
  Это заменяет прежнее решение «общая точка хранится один раз».
  Порядок проверки, точность сравнения, реакция на несогласованные входные данные
  и синхронизация при изменениях ещё не определены; автоматическое исправление
  произвольных входных данных не согласовано.
  Отрисовка самостоятельной и вложенной линии принимает геометрию и материал.
- Маршрут является cross-layer объектом. Предварительная структура:
  segments: [{ layer: "layer-id", lines: [...] }]. Segment — участок маршрута
  на слое, содержащий линии, а не синоним одной линии. Термин sections не нужен.
  Эта предварительная привязка сегментов к слоям пересмотрена ниже: пространственное
  отсечение задаёт сам слой, специальная разбивка маршрута по этажам не требуется.
  Финальная структура segments/lines пока открыта.
- Удаление самостоятельной line не влияет на маршруты.
- Сегмент имеет собственный ID по общим правилам AtlasId: необязателен на входе,
  генерируется при отсутствии, уникален в общем пространстве ID карты и сохраняется
  при экспорте. Это не делает сегмент переиспользуемым внешним объектом.
- При клике на сегмент событие передаёт сам сегмент, родительский маршрут и
  координаты взаимодействия map/client. Приложение решает, показывать описание
  маршрута или конкретного участка. Точная форма payload ещё открыта.
- Точки маршрута хранят координаты, без ссылок на маркеры.
  Перемещение маркера не меняет маршрут: оно не гарантирует читаемость/валидность пути.
- Точки могут опционально иметь label и data и допускать отдельное взаимодействие.
  Обычные точки задают изгибы; значимые — остановки, цели и т. п.
- Наличие label само по себе не задаёт интерактивность; детали Meta для точек открыты.
- У точки маршрута есть необязательный type. Без type это обычная точка изгиба,
  по умолчанию отдельно не рисуется. При наличии type Meta определяет иконку,
  подпись и интерактивность точки. Все точки участвуют в геометрии маршрута.
- Тип точки независим от type маршрута: например, маршрут recommended содержит
  точки quest и extract. Событие точки передаёт её ID, type и ID маршрута.
- Стрелки направления маршрута опциональны и задаются через Meta/материал.
  Направление следует порядку точек от первой к последней; стрелки не задают
  правил проходимости. Точное размещение и частота стрелок пока не определены.
- Отдельного флага замкнутости пока нет: последняя точка может повторять координаты
  первой, имея собственный ID.
- Единое пространство ID для объектов, точек и сегментов; уникальность проверяется по всей карте,
  а не отдельно внутри каждого маршрута.
- id необязателен на входе. Если отсутствует, Atlas генерирует его. Строка "auto" не нужна.
- В runtime у каждого объекта, точки и сегмента есть ID.
- Публичная функция генерации называется AtlasId (вместо предложенного createId).
  Точная сигнатура и алгоритм генерации пока не определены.
- ID — строка, формат MongoDB ObjectId повторять не требуется. Строка «непрозрачная»:
  приложение использует её как идентификатор, не извлекает из внутреннего формата смысл.
- Сгенерированный ID стабилен в течение жизни объекта и сохраняется при экспорте.
  Повторная загрузка исходного JSON без ID создаёт новые ID.
- Для события точки routeId полезен как контекст родителя, pointId идентифицирует точку.

Не завершено: точная схема точек и сегментов, форма payload событий,
их оформление/интерактивность, обработка дубликатов ID, валидация геометрии.
Отдельное скрытие остановки с сохранением геометрии было предложено, но не утверждено.
Примеры из чата — не финальные интерфейсы.

## 5. Слои и этажи — обсуждение продолжается

- Этажи должны поддерживаться в первой версии.
- Термин layer пока не определён. Предложение ассистента трактовать слой только
  как порядок отрисовки не принято. Порядок отрисовки, физические уровни и группы
  фильтрации нужно различить; точный контракт ещё открыт.
- Предложение «один слой на объект, несколько групп» пока не принято.
- Слой понимается как контейнер отображаемого содержимого, а не только порядок
  отрисовки. Есть слой по умолчанию: для простой карты его не нужно явно выбирать.
- Подложка — отображаемое содержимое слоя и подчиняется его видимости вместе
  с остальными объектами. Постоянную подложку можно вынести в отдельный слой,
  который приложение не предлагает переключать.
- Это уточняет предложение ассистента о специальном необязательном поле подложки:
  не фиксируем ни такое поле, ни ограничение «одна подложка на слой».
  Точный kind/контракт объекта подложки ещё открыт.
- Порядок слоёв задаётся stackIndex (название zIndex отвергнуто из-за путаницы
  с координатой высоты z). По умолчанию 0; большие значения поверх меньших;
  отрицательные допустимы; при равенстве последний слой в данных сверху.
  В 2D объекты не выходят поверх слоя с более высоким stackIndex.
- Для будущей 3D-карты этажи могут быть частями модели окружения в отдельных слоях.
  Для полного представления можно включить все такие слои. Все слои находятся
  в едином пространстве карты и используют общую камеру/преобразование всей карты:
  поворот и перемещение не должны независимо вращать этажи вокруг собственных центров.
- Рекомендация ассистента для уточнения 3D-контракта: геометрическое перекрытие
  мировых объектов определять глубиной, не безусловным stackIndex; правила
  композиции, прозрачности и возможных overlay-слоёв ещё не согласованы.

### Уточнение: пространственное отсечение слоями — принято

- Отдельное понятие level не вводится. Сам layer задаёт пространственные границы
  и клипует отображаемую геометрию: например, параллелепипед виден как срез.
- Геометрия использует z и при плоском 2D-отображении. Это универсальное основание
  для отображения частей объектов на этажах, вместо разрезания по stackIndex.
- Требуется именно отображение среза, а не только проверка пересечения и показ
  объекта целиком. Отдельный публичный механизм определения пересечений не требуется;
  внутренний алгоритм clipping ещё не выбран.
- Объект должен описываться целиком, без ручной регистрации ToLayer(object) для
  каждого этажа и без специальной маршрутной разбивки по слоям. Место регистрации
  таких объектов, правила их включения в слои и владение ещё предстоит определить.
- stackIndex остаётся порядком композиции, не пространственной координатой.
- Не определены: форма границ clipping, общие границы соседних слоёв, отображение
  поверхностей среза в 3D, clipping иконок/подписей и идентификация событий срезов.
- Ранние примеры этажей как контейнеров отдельных объектов и segments[].layer
  не являются окончательной схемой; это уточнение имеет приоритет.
- Подтверждена модель: карта хранит общий objects, объект регистрируется один раз
  без обязательных ссылок на слои; слои показывают его геометрию через свои границы clipping.
  Конкретные поля фильтрации/взаимодействия объектов со слоями пока не определены.
- Маршрут упрощён до route.lines[]. Промежуточного массива segments нет.
  Это заменяет ранние схемы route.segments и segments[].lines. Точки хранятся
  внутри линий; маршрут обеспечивает совпадение соседних концов как поведение.
  Линии имеют ID по общим правилам. Событие участка должно идентифицировать
  вложенную линию и маршрут (прежнее название «сегмент» в payload требует уточнения).
- Пример будущего объёмного объекта: kind box, geometry.min/max с x/y/z,
  описывающие целый прямоугольный параллелепипед вдоль осей. Слой отображает его
  срез. Принцип принят, точная схема и включение box в первую версию не утверждены.
- Самостоятельные объекты карты (включая подложки) хранятся в общем objects;
  слои не дублируют их геометрию, а задают выбор содержимого, clipping и stackIndex.
- Слой может брать все объекты либо явно выбранные по ID, после чего применяет
  clipping. Название поля source/objects и точная схема выборки ещё открыты;
  выбор всех объектов по умолчанию предложен, но отдельно не утверждён.
- Вложенные линии остаются внутри маршрута: общий набор самостоятельных объектов
  не превращает внутренние части в независимо переиспользуемые объекты карты.
- Не вводим переопределения position, label (title) и других свойств объекта
  в ссылках слоя. Один объект в нескольких слоях остаётся тем же объектом.
- Повторяющиеся маркеры в разных местах — отдельные объекты с собственными ID,
  позициями и label. Общее оформление задаётся Meta по type.
- Шаблоны и экземпляры для повторного использования сложных объектов могут быть
  добавлены отдельно при появлении сценария; сейчас этот механизм не вводится.
- Принцип разделения: объект описывает себя, слой определяет выбор и отображение
  его содержимого. Возможные особые правила оформления по слоям пока не определены.
- Для событий срезов согласовано передавать ID исходного объекта и ID слоя,
  в котором произошло взаимодействие. Точная форма события ещё открыта.
- clip — необязательное свойство layer. Слой выбирает объекты, затем показывает
  только геометрию внутри clip, не меняя исходные объекты. Без clip отсечения нет.
- Для первой версии clip задаёт область вдоль координатных осей через min/max
  с необязательными ограничениями по x, y, z. Можно указать только диапазон z
  для этажа либо дополнить его границами по x/y; неуказанные ограничения отсутствуют.
  Пример: clip: { min: { z: 3 }, max: { z: 6 } }.
- Произвольные формы clipping отложены.
- Границы clip полуоткрытые: min включается, max исключается по заданным осям.
  Например, маркер с z = 3 принадлежит диапазону [3, 6), а не [0, 3).
  Линии и поверхности обрезаются до самой границы без визуальных щелей;
  правило принадлежности применяется также к подписям и событиям.
- Можно показывать несколько слоёв одновременно. Видимость каждого слоя управляется
  независимо; приложение решает, переключать этажи по одному или включать несколько.
- Объект может иметь необязательный stackIndex для порядка внутри слоя. Больший
  индекс рисуется поверх меньшего; порядок слоёв имеет приоритет. Это порядок
  композиции 2D, правила глубины в 3D обсуждаются отдельно.
- Без stackIndex объекты отображаются в порядке регистрации/создания в Atlas,
  последний поверх предыдущих; при загрузке JSON это порядок в objects.
  Генерировать и записывать stackIndex для этого не требуется. Для сортировки
  отсутствующий индекс трактуется как 0; при равных индексах действует порядок
  регистрации. Пользователь разрешил порядок регистрации вместо генерации индекса.
- При перекрытии цель клика по умолчанию — верхний интерактивный объект под
  указателем с учётом порядка слоёв и объектов. Видимость и участие во взаимодействии
  независимы: видимая подложка/зона может пропускать клики к объектам под ней.
- Скрытые объекты и части геометрии вне clip не участвуют в определении цели.
- Поведение согласовано, но имя interactive, размещение настройки в Meta,
  переопределения на объекте и точный API пока не утверждены.
- Для тонких линий нужна расширяемая область нажатия, независимая от видимой
  толщины штриха. Размер области задаётся в экранных единицах и сохраняет удобство
  попадания при zoom, в том числе на mobile. Внешний вид линии не меняется.
  Настройка позволяет включить/выключить расширение и задать толщину области
  в экранных единицах. Автоматические правила для mobile не вводятся.
  Значения по умолчанию и точный API пока не определены.
- Маркеры (иконки) и подписи по умолчанию сохраняют экранный размер при zoom.
  Опционально можно включить масштабирование вместе с картой. Размер относится
  к отображению, а положение объекта остаётся в пространстве карты.
  Точное размещение этой настройки в контракте ещё не определено.
- Толщина линий и обводок зон по умолчанию сохраняет экранный размер при zoom;
  опционально масштабируется вместе с картой. Сама геометрия (путь маршрута,
  контур полигона, радиус зоны) остаётся в координатах карты и масштабируется
  при приближении. Точный API настройки пока открыт.

## 6. Камера — требования, выявленные при обсуждении слоёв

- Согласованы операции, вызываемые приложением: показать карту целиком
  (подобрать центр и масштаб), сфокусироваться/приблизиться к объекту, вместить
  маршрут или несколько объектов в viewport с экранными отступами.
- Решение когда перемещать камеру остаётся у приложения: оно обрабатывает событие
  и вызывает API камеры. Автоматическая реакция камеры на клик не подразумевается.
- Переходы камеры поддерживают мгновенный и плавный режимы; при вызове можно
  настроить анимацию и её длительность. Значения по умолчанию и точный API открыты.
- Достаточная основа API — задать центр/масштаб и вместить переданную область
  (условный fitBounds с padding). Имена методов, получение bounds объектов
  и поведение при конфликте с ограничениями камеры ещё требуют уточнения.

- Нужна возможность ограничивать камеру; в будущем 3D в том числе запрещать
  неинформативные ракурсы вроде вида снизу. Точные настройки и значения не определены.
- Нужен сохранённый исходный/нормальный вид для быстрого возврата по команде приложения
  (аналог кнопки recenter). Это состояние вида, не начало координат карты.
- Название homeView утверждено; это общий исходный вид для всей карты: центр,
  масштаб и ориентация, где применимо. Предложенная команда resetView() ещё не утверждена.
- Состав ограничений утверждён: bounds перемещения, min/max zoom,
  разрешение/ограничение вращения, для 3D min/max наклон. Реализацию и API обсудим позже.
- Открыто: точное поведение камеры при переключении этажей и выбор исходного вида
  при отсутствии homeView. Сохранение текущей камеры при переключении предложено.
- Пользователь поднял возможность нескольких камер без конкретного сценария.
  Это пока вопрос расширяемости, а не требование первой версии. Следует различать
  сохранённые виды, переключаемые камеры и одновременные viewport с разными камерами.
- Согласовано: одна активная камера на viewport. Это не ограничение одной камерой
  на всю карту: несколько viewport могут одновременно показывать карту с разных камер.
  Камера — отдельная сущность, её состояние не зашито в слои. Реализация нескольких
  одновременных viewport и реестра камер пока не включена в обязательный объём.

## Обновления и runtime-объекты — обсуждение продолжается

- Хранение и восстановление пользовательского состояния — ответственность приложения
  (Redux, MobX и т. п.). Систему снимков сессии в Atlas не вводим. Atlas предоставляет
  текущие значения, события изменений и API управления.
- Подтверждены уведомления об изменениях runtime-объектов: объект, изменённое
  свойство, прежнее и новое значение. Подписка доступна на отдельный объект
  или изменения всей карты, без зависимости от Redux/MobX. Точный API событий открыт.
- Экспорт сериализуемого описания карты остаётся отдельной задачей. Его точный
  состав и граница между сохраняемыми параметрами и временными изменениями
  пока не согласованы; предложение о составе экспорта не считать утверждённым.

- Первоначальная загрузка карты строго валидируется: при некорректных данных
  загрузка отклоняется целиком. Частичный/мягкий режим не вводим.
- Map JSON содержит явное поле schemaVersion (пример: 1), обозначающее версию
  формата данных независимо от версии библиотеки. Неподдерживаемая версия вызывает
  понятную ошибку. Преобразование старых форматов в будущем может выполняться
  отдельными адаптерами; автоматические встроенные миграции не утверждены.
- Ошибка загрузки требуемого ресурса (подложки, иконки и т. п.) также является
  ошибкой загрузки карты. Диагностика указывает ресурс и известную причину сбоя;
  успешная загрузка карты с молча пропущенным ресурсом не допускается.
- При загрузке новой карты текущая остаётся рабочей, пока новые данные проходят
  проверки и загружаются ресурсы. Замена выполняется только после успешной подготовки.
  При ошибке текущая карта сохраняется, приложение получает ошибку загрузки.
- Ошибка загрузки должна информативно указывать, что не прошло проверку и почему.
  Согласованный состав: код ошибки, ID объекта при наличии, путь к проблемному
  полю и причина; ожидаемое и полученное значения указываются, где применимо.
  Точная структура диагностики и стратегия сбора нескольких ошибок ещё открыты.

- По уточнению пользователя не вводим запрет регистрации одного runtime-экземпляра
  в нескольких картах и специальную проверку владельца для такого запрета.
  Повторное использование между картами остаётся ответственностью разработчика.
  Это отменяет обсуждавшееся правило «один экземпляр — одна карта» и ошибку
  OBJECT_ALREADY_ATTACHED. Полноценная синхронизация нескольких карт этим решением
  не обещается; необходимые внутренние связи runtime определим при реализации.

- Неуспешные операции (например, несовпадение концов addLine или дубликат ID)
  выбрасывают исключение с понятным кодом и описанием. Вызывающее приложение
  может обработать его через try/catch; логирование не заменяет исключение.
- Операция, отклонённая валидацией, не меняет состояние объекта. Это гарантия
  отдельной операции, не транзакционность batch; предыдущие успешные изменения
  в batch сохраняются. Классы ошибок и перечень кодов ещё не определены.

- Удаление самостоятельного объекта из карты отсоединяет его и убирает отображение,
  но сохранённая ссылка остаётся рабочим runtime-экземпляром: его можно изменять
  и добавлять обратно. Отсоединение не равно уничтожению.
- Уточнение пользователя заменяет решение о dispose(): публичный dispose для
  runtime-объектов не вводим. Приложение само решает, сохранять ли ссылку;
  недостижимый объект освобождается GC.
- Отсоединение сопровождается событием; название, получатель и payload ещё открыты.
  Atlas должен освободить собственные удерживающие ссылки и привязки к карте
  (индексы, рендеринг, подписки и т. п.), сохраняя работоспособность экземпляра
  при наличии внешней ссылки. Очистка renderer-ресурсов — внутренняя ответственность,
  не обязанность пользователя вызывать dispose на каждом объекте.
- Такое разделение может использовать будущий редактор для undo/redo; само
  undo/redo в ядре этим решением не добавляется.

- Добавление, изменение и удаление объектов должны обновлять карту инкрементально.
  Это механизм runtime/renderer, независимый от изоляции Shadow DOM.
- batch утверждён: несколько изменений можно объединить с отложенным обновлением
  отображения. Во время callback данные меняются сразу, обновление отображения
  приостановлено; после завершения callback Atlas обновляет затронутое отображение.
  Это не транзакция: предыдущие успешные изменения не откатываются при ошибке.
  События отправляются сразу после каждого успешного изменения; обработчики видят
  актуальные данные и могут выполнять связанные изменения. batch приостанавливает
  только отрисовку, не поведение объектов и события.
  Вложенные batch поддерживаются: отрисовка возобновляется только после выхода
  из самого внешнего batch. Callback синхронный; async batch не поддерживается.
  Асинхронные данные приложение получает до batch, затем синхронно применяет изменения.
  Точная сигнатура и диагностика ошибочного async callback ещё открыты.
- Пользователь выбирает runtime-экземпляры с поведением: регистрация объекта должна
  возвращать ссылку на экземпляр, который приложение может сохранить и изменять.
  Поиск по ID должен предоставлять такой экземпляр, а не только plain JSON.
- Сериализуемый Map JSON остаётся форматом входных/выходных данных; runtime-экземпляр
  с методами/наблюдаемыми свойствами — отдельное представление того же объекта.
- Обсуждаемый API: map.object(id).update(...), методы экземпляра и сеттеры,
  включая marker.position.x = 50. Точная поддержка вложенных сеттеров и коллекций,
  семантика patch/update и стабильность вложенных ссылок ещё не согласованы.
- Прежнее предложение ограничиться map.updateObject(id, patch) и отсутствием
  реакции на любые мутации не принято. Мутация исходного входного JSON и мутация
  runtime-экземпляра — разные операции; точные правила нужно сформулировать.
- Принято: route.lines — собственная стабильная runtime-коллекция с предметными
  методами и поддержкой итерации. Основной путь добавления — route.lines.add(description).
  Коллекция не имитирует Array API (push/splice и т. п. не вводятся).
- Изменения состава коллекции проходят через правила маршрута: валидацию,
  поддержание связности и уведомление об изменениях. Прямые изменения геометрии
  вложенных линий также должны соблюдать правила владельца.
- for...of позволяет обходить линии; преобразование в массив создаёт отдельный
  массив, но его элементы остаются ссылками на runtime-экземпляры линий.
- Предложение getter с одноразовым генератором и отдельными route.addLine/removeLine
  заменено API коллекции. Точные сигнатуры удаления, перестановки и поиска,
  возвращаемое значение add и семантика итерации при изменениях ещё открыты.
- Последующее уточнение для связного маршрута имеет приоритет над route.lines.add:
  пользователь выбрал две операции маршрута — addLine и addPoint.
- route.addLine принимает полное описание линии и добавляет её в конец пути только
  если начало совпадает с текущим концом маршрута; при несовпадении отклоняет операцию,
  не исправляя геометрию. Форма отказа и точность сравнения пока открыты.
- route.addPoint({x, y, z}) использует последнюю точку маршрута как начало новой
  линии, а переданную — как конец, затем добавляет линию в маршрут.
- Для пустого маршрута первый addPoint задаёт стартовую точку, второй создаёт
  первую линию. Первый addLine добавляется без проверки предшественника,
  с обычной валидацией самой линии. Представление стартовой точки до появления
  первой линии в сериализуемых данных ещё не определено; route.points не возвращаем.
- API чтения route.lines, удаления/вставки и изменения уже существующих линий
  ещё требует согласования.
- Принято для изменения общей точки: перемещение конца линии автоматически
  перемещает начало следующей; перемещение начала — конец предыдущей.
  Маршрут синхронизирует координаты в обе стороны, сохраняя связность без общего
  реестра точек. Это изменение существующего пути, а не исправление несовпадающей
  новой линии в addLine: такая вставка по-прежнему отклоняется.
- Согласованы два отдельных метода изменения непрерывного участка маршрута:
  замена (replace) и удаление; точные имена, аргументы и возвращаемые значения открыты.
- Замена принимает последовательность новых линий, образующих связный путь.
  Начало и конец нового участка должны совпадать с крайними точками заменяемого;
  при несовпадении операция отклоняется.
- Для сравнения координат при проверке связности необходим допуск к погрешностям
  floating point; строгое числовое равенство не используем. Конкретное значение,
  абсолютная/относительная метрика и настройка допуска ещё открыты.
  Если начало новой линии совпадает с концом предыдущей в пределах допуска,
  приводим его к точным координатам предыдущего конца, устраняя микроразрыв.
  При расхождении сверх допуска операция отклоняется.
- Удаление внутреннего участка заменяет его одной прямой между крайними точками.
  Удаление участка в начале или конце просто убирает его, без соединительной линии.
  Удаление всего пути оставляет пустой маршрут.
- Это правило заменяет предварительное предложение запрещать удаление из середины.
  Соединительная прямая сохраняет связность, но не гарантирует проходимость по местности.
  Перенос label/data/type, выбор материала и идентичность созданных/удалённых частей
  при таких операциях ещё предстоит определить.

## Оформление — уточнение вместо Meta

### Актуальное решение: явные связи материалов

- Принята основа: именованные материалы, явное наследование и назначение материала
  объекту. Имя вроде line.base — произвольный идентификатор; точка не задаёт
  иерархию. Связь задаётся явно через родителя (условное поле inherits).
- Незаданные свойства наследуются от явно указанного родителя; собственные
  значения материала переопределяют наследуемые. Встроенные материалы сохраняют
  возможность использовать карту без ручного оформления.
- Мотивация: явные зависимости и инкапсуляция вместо неявного CSS-подобного каскада.
- Подтверждено: специфичность kind → kind + type → объект выбирает один назначенный
  материал, а не смешивает свойства материалов этих уровней. Свойства разрешаются
  только по явной цепочке наследования выбранного материала.
- Для kind есть встроенный материал; приложение может назначать материалы по
  kind/type и явно конкретному объекту. Конкретное назначение имеет приоритет.
  Например: marker {color: gray, size: 24}; extract inherits marker и задаёт green;
  special inherits extract и задаёт size: 32. Объект с special зелёный размером 32.
  Точная схема таблицы назначений ещё не определена.
- Маршрут задаёт материал по умолчанию для своих линий. Отдельной линии можно
  назначить другой материал; он заменяет выбор маршрута, без неявного смешивания
  свойств. Наследование свойств по-прежнему задаётся только через inherits.
  Конкретный механизм/API переназначения обсудим позже — пользователь явно
  оставил его открытым.

### Decision points: операции над материалами и поведение

- alter/replace/reset возвращены в открытые decision points: прежняя условно
  принятая семантика ниже сохранена как история, не как окончательное обязательство API.
- alter: нужен ли отдельный метод объединения свойств, если явное наследование
  уже позволяет описывать частичные переопределения? Изменение runtime-свойств
  и описание наследования — разные операции; окончательный API не выбран.
- replace: что именно заменяется — назначенный материал, параметры экземпляра
  или временное оформление поведения? Область действия ещё не определена.
- reset: к какому состоянию возвращаться и какие изменения снимать? Общий reset
  не должен неявно отменять независимые изменения приложения или других поведений.
- Hover и другие эффекты рассматриваем вместе с будущей регистрацией поведения:
  эффект может задаваться зарегистрированным поведением либо изменением свойства.
  Нужно определить применение/снятие эффекта и композицию одновременных изменений.
- Пользователь привёл эти замечания как контекст архитектурного направления,
  а не запрос немедленно определить сигнатуры или реализовать систему.

Последнее уточнение: пользователь возвращает термин material/materials вместо styles.
Не вводим отдельную концепцию стилей поверх ранее выбранных материалов.
Точные имена API и разделение реестра материалов и правил назначения ещё обсуждаются.
Приняты три уровня применения: kind → kind + type → конкретный объект;
более конкретный уровень переопределяет указанные свойства. Встроенное оформление,
частичные переопределения и обновление независимо от данных сохраняются.
Пользователь подтвердил специфичность как подход Atlas, который можно адаптировать
позже. Source/Unreal обсуждались только как примеры; повторять их архитектуру,
shader graphs или иерархию material instances не требуется.
Упоминания styles ниже описывают предыдущий вариант названия и уступают этому уточнению.

- Согласован публичный термин styles для правил оформления. Название theme
  не используем как основной контракт. Прежний контейнер Meta требует пересмотра;
  его упоминания выше отражают прежние обсуждения, а не финальный API.
- Atlas предоставляет встроенное оформление: карта работает без пользовательских
  стилей. Базовые стили покрывают поддерживаемые kind, подписи, точки маршрута
  и подсветку. Неизвестный semantic type получает базовое оформление своего kind.
- Пользовательские styles переопределяют только нужные части встроенного оформления;
  полный набор правил от приложения не требуется.
- Styles можно задать при создании карты и менять во время работы независимо
  от данных объектов, без их пересоздания. Условный пример: map.styles = customStyles.
- Styles — собственный renderer-independent контракт Atlas, не CSS.
  Материалы могут остаться внутренней/составной концепцией, но точная структура,
  приоритеты правил и механизм обновления styles ещё не определены.
- Оформление отделено от обработки событий и поведения; прежние behaviors в Meta
  не переносятся автоматически в styles.
- Текущая согласованная семантика runtime-материала объекта:
  alter(properties) объединяет локальные переопределения, меняя только переданные
  свойства (не арифметическое сложение); replace(properties) полностью заменяет
  локальные переопределения; reset() удаляет их и возвращает оформление,
  разрешённое через kind/type и встроенные значения.
- Незаданные после replace свойства наследуются из базового материала, а не
  становятся неопределёнными. Изменение object.material касается только этого
  объекта и не меняет общий материал других объектов.
- Приложение может вызывать эти операции при hover/click или других событиях;
  специальные встроенные состояния hovered/selected для этого не требуются.
  Детали вложенных свойств и управления несколькими одновременными эффектами
  ещё не определены. Пользователь принял эту семантику как текущую («пока да»).
- Направление расширения, подтверждённое пользователем: регистрация именованных
  поведений/классификаторов для гибкой связи событий, состояний и материалов.
  Hover — возможный пример, а не обязательный фиксированный набор состояний.
  Пользовательский пример XXX.register("hover", onClick()) иллюстрирует идею,
  не задаёт конкретную сигнатуру или смешение семантик событий и состояний.
- Текущих alter/replace/reset достаточно для согласованных требований. К устройству
  расширяемой системы вернёмся отдельно: приоритеты состояний, снятие эффектов,
  жизненный цикл регистраций и связь с материалами ещё не определены.
  Предложение хранить функции в runtime и имена в JSON соответствует общей
  сериализуемой модели, но точный контракт регистрации пока не утверждён.
- Автоматическое распространение изменений общего материала с сохранением локальных
  переопределений было предложено, но отдельного подтверждения пока нет.

## Диагностика

### Принципы расширяемой системы свойств и материалов

- Расширения регистрируются в отдельной конфигурации Atlas, а не в глобальном
  реестре страницы. Конфигурацию можно использовать для одной или нескольких карт;
  независимые конфигурации не влияют друг на друга. Встроенные возможности доступны
  по умолчанию и не требуют регистрации приложением.
- Пользовательские свойства, поведения и будущие адаптеры совместимости
  регистрируются до создания карты. Регистрация определяет смысл свойства,
  допустимые значения и обработку; изменение значений runtime-объектов и материалов
  после создания карты остаётся возможным.
- Изменение самих регистраций во время работы карты пока не поддерживается.
  Точный API конфигурации и механизм фиксации её регистраций ещё не определены.
- Повторная регистрация свойства/поведения с тем же именем в соответствующем
  реестре одной конфигурации отклоняется с понятной ошибкой; молчаливой замены нет.
  Это правило относится к определениям, не к изменению значений свойств.
  Явный механизм намеренной замены встроенной регистрации оставлен на будущее.
- Неизвестное свойство в структурных данных Atlas или материале является ошибкой
  с указанием имени и пути. Это выявляет опечатки и отсутствующие регистрации
  расширений. Ключи внутри пользовательского data не проверяются на принадлежность
  реестру Atlas; требование JSON-сериализуемости data сохраняется.
- При регистрации свойства обязательно указывается область применимости:
  объект/тип объектов или несколько, для которых оно поддерживается. Применение
  известного свойства к неподходящему объекту отклоняется с понятной ошибкой.
  Точный способ указания (kind, классы, возможности или конкретные ID) ещё не выбран.
- Публичный список зависимостей для пересчёта при регистрации свойств не вводим.
  Atlas и поведение узла сами организуют обновления, используя внутренние признаки
  изменений: геометрии, bounding box, оформления и т. п. Например, изменение цвета
  не требует пересчёта геометрии. Конкретный алгоритм инвалидации — деталь реализации.
  Это не возобновляет отложенные привязки значений между свойствами.
- Для подписи подтверждено разделение сериализуемого описания и runtime-объекта
  с поведением. Это развивает общее разделение Map JSON и runtime-экземпляров.
- Подтверждена только явная объектная форма label в JSON, например
  label: { text: "Выход" }. Строковое сокращение и его автоматическое преобразование
  не поддерживаем. Это заменяет прежние примеры label как строки.
  Конкретный полный набор параметров размещения/оформления и их API ещё открыт.
- Подпись является частью своего объекта, а не самостоятельным объектом карты.
  Клик по подписи считается кликом по владельцу; отдельный label-click и признак
  part: "label" пока не вводим, поскольку нет конкретного сценария. Отдельный
  публичный ID подписи для взаимодействия не требуется.
- Размещение и читаемость подписей — ответственность автора карты. В первой версии
  не вводим автоматическое устранение пересечений, смещение или скрытие подписей.
  Будущее управление видимостью подписей (например, в зависимости от zoom)
  отложено; конкретный механизм пока не проектируем.

- Подтверждены направления из MATERIAL_SYSTEM_EXPLORATION.md: типизированные
  свойства с defaults/enum/валидацией и проверкой применимости; явные контракты
  оформления узлов; группировка связанных параметров; предоставляемые контракты
  оформления частей составного объекта; небольшое ядро и стандартные расширения.
  Конкретные схемы и API ещё открыты. Изоляция и явное наследование уже приняты ранее.
- Регистрация свойств/поведение подписи остаются направлением proof of concept.
- Нужен механизм deprecation: свойства можно помечать устаревшими и предупреждать
  при их использовании. Формат metadata и политика предупреждений ещё открыты.
- Перспектива: подключаемые polyfills/адаптеры совместимости для удалённых свойств,
  чтобы не держать устаревшие реализации в ядре. Конкретный контракт ещё не выбран.
- Привязки между свойствами, параметризованный язык, селекторы и общий layout engine
  явно отложены пользователем; не включаем их в текущий объём.

- Пользователь согласовал необходимость proof of concept регистрируемых свойств
  на примере label. Это направление проверки, не команда начать реализацию.
- Пользователь хочет подробную диагностику валидатора при разработке, менее
  подробную в runtime и возможность отключения. Какие проверки отключаемы,
  ещё необходимо согласовать со строгой загрузкой и гарантиями операций.
  Предложение ассистента отключать только дополнительные проверки расширений,
  сохраняя обязательные проверки корректности, отдельно не подтверждено.
- Анализ прежнего наброска собственной системы оформления сохранён отдельно:
  [MATERIAL_SYSTEM_EXPLORATION.md](../MATERIAL_SYSTEM_EXPLORATION.md).
  По запросу пользователя полноценная самостоятельная система стилей/материалов
  отмечена как сильно далёкое будущее, не объём первой версии Atlas.

Требование пользователя: console logging с тремя уровнями и возможностью полного отключения.

Предложено, но отдельно не подтверждено: error / warn / debug, настройка
off | error | warn | debug, накопительное включение уровней, default warn,
префикс [Atlas]. Финальный контракт конфигурации открыт.

## План следующих обсуждений

## Граница runtime / renderer — согласовано

- Runtime отвечает за объекты и их поведение, валидацию, разрешение материалов
  и наследования, слои/видимость/границы clip, состояние камеры, нормализованные
  события, учёт изменений и batch.
- Renderer отвечает за отрисовку конкретной технологией, перевод параметров
  материалов, применение clipping и проекции камеры, определение объекта под
  указателем и обновление затронутого отображения.
- Renderer получает подготовленное описание отображения и возвращает результат
  определения цели взаимодействия; не определяет бизнес-поведение объектов,
  изменение маршрутов или реакцию приложения на клик.
- Начинаем с SVG-renderer и проверяем контракт на нём. Будущие backend подключаются
  через эту границу; точные интерфейсы пока не определены.
- Обсуждение продолжаем крупными блоками; конкретные идеи пользователя сохраняем
  как решения или decision points, не теряя их до проектирования сигнатур.

## Статус и оставшиеся обсуждения

Текущий статус: первый проход архитектурных требований, не финальные интерфейсы
и не реализация. Основа блоков 1–7 определена; блоки 8–9 частично проработаны,
блок 10 ещё впереди. Обсуждение шло не строго линейно. Оценка готовности первого
прохода — примерно две трети, не оценка готовности библиотеки.

Остаток первого прохода: минимальные контракты материалов/свойств и label;
целостный API компонента, runtime-объектов и событий; renderer/extension boundary;
ресурсы и точный состав сериализации; доступность/устройства/нагрузка;
границы и критерии prototype. Затем консолидировать документ, убрать противоречия
между историческими и актуальными решениями и вынести отложенные вопросы отдельно.

1. Сценарии первой версии — закрыто.
2. Подложка и координаты — направление согласовано, интерфейсы позже.
3. Объекты — основание согласовано.
4. Маршруты и точки — основа согласована, точные схемы и валидация позже.
5. Слои, этажи, видимость, группы и порядок отрисовки — текущий пункт.
6. Камера, пределы zoom/pan, начальный вид, фокусировка, экранные/мировые размеры.
7. Состояние и владение им; будущие потребности отдельного редактора.
8. Meta, материалы, подписи, состояния подсветки и загрузка ресурсов.
9. Публичный API, события, renderer/coordinate contracts и расширения.
10. Проверочный прототип: объём данных, браузеры, доступность, критерии проверки.

Для прототипа потребуются подложка, несколько маркеров с известными координатами
и маршрут с изгибами и значимыми остановками.
