## 2. Пространство и окружение — согласовано

- Формат Atlas независим от сторонних форматов; импортеры преобразуют исходные данные.
- Пример источника: https://github.com/the-hideout/tarkov-dev ; пример UX:
  https://tarkov.dev/map/customs . Это референсы, а не обязательные зависимости.
- Пространство карты независимо от разрешения изображения. Координаты могут быть
  дробными и отрицательными; единицы определяет карта/импортер.
- По умолчанию (0, 0) сверху слева, x вправо, y вниз, z — высота вверх.
  Неуказанный z считается 0. Границы задаются отдельно от разрешения изображения.
- Другие системы координат поддерживаются через преобразование; точный контракт открыт.
- Первая версия: raster- или SVG-подложки с размещением в пространстве карты.
  Этажи нужны уже в первой версии (уточнение пользователя после обсуждения маршрутов).
  Прежнее ограничение одной подложкой требует пересмотра: способ представления
  подложек этажей и переключения между ними пока не согласован.
  Управление крышами не требуется. Тайлы и внутренние слои SVG пока не входят в объём;
  необходимость работы со слоями SVG для этажей ещё следует оценить.
- Пространство карты, окружение, семантические объекты и камера разделены.
- Дальнейшая цель — настоящая объёмная местность, рельеф и модели, а не только
  наклон плоской картинки. При необходимости картинка может быть плоскостью в 3D.
- Предусмотреть контракт расширения/рендерера для 3D; конкретный интерфейс будет
  обсуждаться позже. Полную 3D-реализацию сейчас не проектируем.
- Пользователь хочет возможность кастомизации pipeline преобразований; границы
  расширения, согласование отрисовки и hit testing ещё требуют проектирования.
- В 3D экранная точка задаёт луч: обратному преобразованию нужна поверхность или
  плоскость пересечения. Высота/привязка маршрутов к поверхности остаётся открытой.
- Полупрозрачность 3D-окружения рассматривается как будущая возможность;
  поведение hit testing для него пока не определено.

## 3. Объекты — согласовано

- Общие поля: id, kind, type, необязательные label и data.
  id необязателен во входных данных — см. раздел идентичности.
- kind описывает структуру; type свободно задаётся приложением.
- data — произвольные сериализуемые JSON-данные приложения.
- label — стандартная необязательная подпись; Atlas может её рисовать.
  Оформление определяется через Meta/материалы.
- marker: position { x, y, z? }; может отображаться только подписью без иконки.
- line: самостоятельный объект карты, например разделительная линия; владеет
  собственной геометрией, имеет общие поля объекта, события и видимость.
- route: составной объект с упорядоченными сегментами по слоям; каждый сегмент
  содержит линии. В первой версии линии прямые; детали состава описаны ниже.
- polygon: один замкнутый заполненный контур без отверстий.
- circle: центр и радиус в единицах карты.
- Название места без границ — marker с label; подпись существующей зоны принадлежит
  polygon/circle, чтобы зона и подпись оставались единым объектом.
- Кривые Безье — будущее расширение геометрии; могут относиться к маршрутам и контурам.
- Точная схема полей геометрии и расширяемость kind ещё не завершены.

## 4. Маршруты и идентичность — обсуждение продолжается

Принято:

- Route инкапсулирует свои сегменты. Это не ссылки на самостоятельные line на карте;
  сегменты не переиспользуются между маршрутами.
- Самостоятельная line и линии внутри сегментов используют общую модель геометрии, оформления
  и код отрисовки. Линия не обязана знать, используется ли она внутри маршрута.
- Толщина, цвет, пунктир и стрелки относятся к материалу линии. Маршрут обеспечивает
  оформление по умолчанию; сегмент может переопределять его. Точная схема открыта.
- Маршрут отвечает за поведение принадлежащих ему частей: скрытие маршрута скрывает
  сегменты и точки, общая подсветка и оформление координируются маршрутом.
- Уточнение пользователя: маршрут обеспечивает связность как поведение/правило,
  а не через общий реестр точек. Отдельного route.points нет. Точки хранятся
  в геометрии линий; маршрут следит за совпадением концов соседних линий.
  Это заменяет прежнее решение «общая точка хранится один раз».
  Порядок проверки, точность сравнения, реакция на несогласованные входные данные
  и синхронизация при изменениях ещё не определены; автоматическое исправление
  произвольных входных данных не согласовано.
  Отрисовка самостоятельной и вложенной линии принимает геометрию и материал.
- Маршрут является cross-layer объектом. Предварительная структура:
  segments: [{ layer: "layer-id", lines: [...] }]. Segment — участок маршрута
  на слое, содержащий линии, а не синоним одной линии. Термин sections не нужен.
  Эта предварительная привязка сегментов к слоям пересмотрена ниже: пространственное
  отсечение задаёт сам слой, специальная разбивка маршрута по этажам не требуется.
  Финальная структура segments/lines пока открыта.
- Удаление самостоятельной line не влияет на маршруты.
- Сегмент имеет собственный ID по общим правилам AtlasId: необязателен на входе,
  генерируется при отсутствии, уникален в общем пространстве ID карты и сохраняется
  при экспорте. Это не делает сегмент переиспользуемым внешним объектом.
- При клике на сегмент событие передаёт сам сегмент, родительский маршрут и
  координаты взаимодействия map/client. Приложение решает, показывать описание
  маршрута или конкретного участка. Точная форма payload ещё открыта.
- Точки маршрута хранят координаты, без ссылок на маркеры.
  Перемещение маркера не меняет маршрут: оно не гарантирует читаемость/валидность пути.
- Точки могут опционально иметь label и data и допускать отдельное взаимодействие.
  Обычные точки задают изгибы; значимые — остановки, цели и т. п.
- Наличие label само по себе не задаёт интерактивность; детали Meta для точек открыты.
- У точки маршрута есть необязательный type. Без type это обычная точка изгиба,
  по умолчанию отдельно не рисуется. При наличии type Meta определяет иконку,
  подпись и интерактивность точки. Все точки участвуют в геометрии маршрута.
- Тип точки независим от type маршрута: например, маршрут recommended содержит
  точки quest и extract. Событие точки передаёт её ID, type и ID маршрута.
- Стрелки направления маршрута опциональны и задаются через Meta/материал.
  Направление следует порядку точек от первой к последней; стрелки не задают
  правил проходимости. Точное размещение и частота стрелок пока не определены.
- Отдельного флага замкнутости пока нет: последняя точка может повторять координаты
  первой, имея собственный ID.
- Единое пространство ID для объектов, точек и сегментов; уникальность проверяется по всей карте,
  а не отдельно внутри каждого маршрута.
- id необязателен на входе. Если отсутствует, Atlas генерирует его. Строка "auto" не нужна.
- В runtime у каждого объекта, точки и сегмента есть ID.
- Публичная функция генерации называется AtlasId (вместо предложенного createId).
  Точная сигнатура и алгоритм генерации пока не определены.
- ID — строка, формат MongoDB ObjectId повторять не требуется. Строка «непрозрачная»:
  приложение использует её как идентификатор, не извлекает из внутреннего формата смысл.
- Сгенерированный ID стабилен в течение жизни объекта и сохраняется при экспорте.
  Повторная загрузка исходного JSON без ID создаёт новые ID.
- Для события точки routeId полезен как контекст родителя, pointId идентифицирует точку.

Не завершено: точная схема точек и сегментов, форма payload событий,
их оформление/интерактивность, обработка дубликатов ID, валидация геометрии.
Отдельное скрытие остановки с сохранением геометрии было предложено, но не утверждено.
Примеры из чата — не финальные интерфейсы.

## Выбор полей data

Обсуждались jq-подобные выражения и простые селекторы полей.
Рекомендация ассистента: пока не вводить язык выборки; приложение/импортер готовит label
и другие стандартные значения. Пользователь явно не утвердил отдельный контракт селекторов.
